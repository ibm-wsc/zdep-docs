#CICS GenApp

The CICS GenApp image is a pre-configured z/OS 3.2 environment with the CICS General Insurance Application (GenApp) installed and ready to use, and with z/OS Connect 3.0.98 configured as an API provider that exposes GenApp as REST APIs. It is built on top of the z/OS Standard Image (z/OS 3.2), with CICS and Db2 included directly in this image, and is available on TechZone for CICS demonstrations, API-first application modernization walkthroughs, and COBOL application development.

GenApp is a working COBOL application originally developed by the IBM Hursley CICS Development team. It simulates a general insurance company processing customer and policy records — querying, inserting, and deleting records through a 3270 interface and through REST APIs served by z/OS Connect.

#What's Included

  • z/OS 3.2 — See Base z/OS Configuration for the full system layout
  • CICS Transaction Server 6.3 — Region pre-configured with CICS System Management Single Server (SMSS), CMCI, and RACF security
  • Db2 for z/OS Version 13 — Pre-wired to the CICS region via a DB2CONN resource for EXEC SQL processing
  • CICS GenApp — Installed and configured in the CICSTS1 region, with Db2 tables created and CICS resources loaded into the CSD
  • 3270 interface — SSC1, SSP1, SSP2, SSP3, and SSP4 transactions available on any 3270 terminal connected to CICSTS1
  • z/OS Connect 3.0.98 — Installed to /usr/lpp/IBM/zosconnect/v3r0 (zFS BAQ30E.REL.ZFS, mounted read-only)
  • z/OS Connect server defaultServer — Created from the zosconnect:openApi3 template and configured as an OpenAPI 3.0 provider for GenApp
  • GenApp API provider — The genapp_provider.war application deployed at context root /genapp, with operations for customers and for motor, house, endowment, and commercial policies
  • CICS IPIC connection — A TLS-secured IPIC connection between z/OS Connect and the CICSTS1 region, defined in CICS as the NAPP IPCONN and the OAS3GENA TCPIPSERVICE
  • Liberty Angel process — BAQANGL started task, required for z/OS authorised services
  • RACF security — GenApp user profiles and resource authorisations, plus users, group, and resource profiles for the angel and server started tasks and a SAF key ring with TLS certificates for the server
  • Autostart — CICS region, Db2 subsystem, and the z/OS Connect angel and server started tasks start automatically at IPL

For the full product list including FMIDs, see Installed Products.

#Application Overview

GenApp models a general insurance company with four types of insurance policy — house, motor, commercial, and endowment. The application provides a 3270 menu-driven interface for:

FunctionDescription
Inquire customerLook up a customer by customer number
Add customerCreate a new customer record
Inquire policyRetrieve a policy record by customer and policy number
Add policyCreate a motor, commercial, or endowment policy
Delete policyRemove a policy record

Policy and customer data is stored in both a VSAM file and a Db2 table.

#Architecture

REST client ──HTTPS 9443──▶ z/OS Connect (BAQSTRT / defaultServer)
                                   │  /genapp  (genapp_provider.war)
                                   │
                                   └─ IPIC over TLS, 127.0.0.1:30250 ─▶ CICSTS1 (OAS3GENA TCPIPSERVICE, NAPP IPCONN)
                                                                               │
                                                                               └─▶ GenApp COBOL programs ─▶ Db2 (DBA1) / VSAM

z/OS Connect is configured on top of the CICS GenApp environment to expose GenApp's customer and policy operations as REST APIs, described by an OpenAPI 3.0 document. The 3270 interface remains available alongside the REST APIs.

#Accessing GenApp via 3270

Connect a 3270 emulator to your z/OS instance (see Connecting to Your Instance). You will land on the z/OS VTAM logon screen.

#Logging on to CICS

Rather than logging on to TSO, connect directly to the CICSTS1 CICS region:

LOGON APPLID(CICSTS1)

You will be prompted for credentials. Enter your user ID and password:

FieldValue
User IDZOSADMN
Password(from your TechZone reservation details)

Note: The password field will not display any characters as you type — this is expected behaviour.

After a successful sign-on you will see the CICS blank screen, ready to accept transactions.

#Testing the Application

The following steps walk through a quick end-to-end verification of GenApp to confirm the application, Db2, and VSAM are all working correctly.

  1. Log on to CICS — Follow the steps to logon if you haven't already.

  2. Open the customer menu — Type SSC1 and press Enter.

  3. Inquire on customer 1 — In the Cust Number field enter 1 (displayed as 0000000001), tab down to Select Option, enter 1, and press Enter.

  4. The customer record will be returned:

    If the record is displayed, GenApp is correctly installed and connected to Db2 and VSAM.

  5. Press F3 to exit any menu screen.

#Testing the API

Once the instance is running, retrieve customer 1 (the same record used in the 3270 test) using the z/OS Connect HTTPS endpoint:

curl -k -u ZOSADMN:<password> https://<instance-ip>:9443/genapp/customers/1
  • Use the ZOSADMN user ID and the password from your TechZone reservation details.
  • -k is needed because the server certificate is signed by a self-signed CA created on the instance (see TLS Certificates).
  • A successful response returns the customer record from Db2, confirming that z/OS Connect, CICS, and Db2 are all working together.

Policies can be retrieved in the same way using the Sample Data above, for example /genapp/policies/motor/1.

#CICS Connectivity

z/OS Connect communicates with GenApp in CICS using an IPIC connection on the loopback address. The CICS resources are defined in CSD group GENAZCEE, which is added to CSD list GENALIST so that they are installed automatically when the CICS region starts.

ResourceTypeKey attributes
OAS3GENATCPIPSERVICEPort 30250, protocol IPIC, SSL=YES, certificate CICSPRDCERT, transaction CISS
NAPPIPCONNAPPLID GENAPP, NETWORKID LOCAL, SSL=YES, certificate CICSPRDCERT, USERAUTH=LOCAL, security name ZOSADMN

On the z/OS Connect side, the cicsConn zosconnect_cicsIpicConnection in server.xml connects to 127.0.0.1:30250 with zosConnectApplid="GENAPP" and zosConnectNetworkid="LOCAL".

#z/OS Connect Security

#RACF

  • Group LIBGRP with OMVS segment (AUTOGID), owned by SYS1.
  • Users BAQANGL (angel) and LIBSERV (server), both with default group LIBGRP, an OMVS segment (AUTOUID), and no password.
  • STARTED class profiles BAQANGL.* and BAQSTRT.* associating each started task with its user ID.
  • SERVER class profiles BBG.ANGEL, BBG.ANGEL.BAQANGL, BBG.AUTHMOD.BBGZSAFM*, BBG.AUTHMOD.BBGZSCFM*, and BBG.SECPFX.BBGZDFLT, with READ access for LIBSERV.
  • FACILITY class profiles BPX.SMF and IRR.DIGTCERT.LISTRING, with READ access for LIBSERV.
  • SURROGAT profiles BPX.SRV.LIBSERV and LIBSERV.SUBMIT, with READ access for ZOSADMN.
  • UNIXPRIV access for ZOSADMN to SUPERUSER.FILESYS (CONTROL) and SUPERUSER.FILESYS.CHOWN (READ).

The server authenticates and authorises users through SAF (safRegistry, safAuthorization, and safCredentials with profile prefix BBGZDFLT), so API callers sign on with their z/OS user ID and password.

#TLS Certificates

The LIBSERV user owns the key ring Liberty.KeyRing, which is used by the server as its key store and trust store (safkeyring:///Liberty.KeyRing).

LabelPurpose
zosConnectCACertificate authority created for the instance (CN=CA for LTE1.LOCALDOMAIN, O=IBM, OU=Z Demo Enablement Program, C=US), expires 2030-12-31
zosConnectServerCertServer personal certificate (CN=LTE1.LOCALDOMAIN) signed by zosConnectCA, expires 2030-12-31
CICSPRDCERTCICS certificate (owned by CICSPRD) connected to the key ring as a trusted CA so that z/OS Connect trusts the CICS IPIC TLS connection

Warning: The zosConnectServerCert personal certificate is signed by zosConnectCA, a private CA that clients do not trust by default. When a client first connects to the HTTPS port (9443), it cannot validate the certificate chain and aborts the handshake with a certificate_unknown alert, and the server logs a CWWKO0801E SSL handshake error in messages.log. For example, this happens when your browser displays its certificate warning, even if you then choose to proceed and trust the certificate, because the warning is shown after the initial handshake has already been rejected. These errors are expected and can be ignored. To avoid them, import the zosConnectCA certificate into the client's trust store, or replace the server certificate with one signed by a trusted CA.

#Verifying the CICS Region is Active

To confirm the CICSTS1 region is up, from a 3270 operator console:

D A,CICSTS1

Or from USS via SSH:

opercmd "D A,CICSTS1"

Then follow the Testing the Application steps above to verify end-to-end connectivity.

#Verifying z/OS Connect is Active

From a 3270 operator console:

D A,BAQSTRT
D A,BAQANGL

Or from USS via SSH:

opercmd "D A,BAQSTRT"
opercmd "D A,BAQANGL"

To restart the server, stop and start the started task:

C BAQSTRT
S BAQSTRT

Then follow the Testing the API steps above to verify end-to-end connectivity. If the API returns an error, confirm that the CICSTS1 region is active and that the OAS3GENA TCPIPSERVICE and NAPP IPCONN are installed and in service (see Verifying the CICS Region is Active).

#Autostart and IPL Persistence

  • The CICS region and Db2 subsystem start automatically at IPL.
  • The BAQANGL and BAQSTRT started tasks are started automatically at IPL through COM='S BAQANGL' and COM='S BAQSTRT' entries in SYS1.PARMLIB(COMMND00).
  • The zFS file systems are mounted automatically at IPL through entries added to SYS1.PARMLIB(BPXPRMZ2): BAQ30E.REL.ZFS (read-only) at /usr/lpp/IBM/zosconnect/v3r0 and OMVS.ZCEE.ZFS (read-write) at /var/zosconnect.
